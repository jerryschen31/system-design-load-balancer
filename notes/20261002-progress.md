## 3. Phase-by-phase

### Phase 1 — single-backend reverse proxy (Aug 21)
**Built:** the smallest correct request path. A Layer 7 (HTTP) proxy that forwards every request to one fixed backend, with a logging middleware and graceful shutdown.
**Concepts:** L4 vs. L7 proxying (chose L7 because caching and per-client rate limiting need HTTP-level information); what a socket actually is in the kernel; hop-by-hop vs. end-to-end headers; why a proxy must not trust a client-supplied `X-Forwarded-For`.
**Left out on purpose:** multiple backends, health checks, rate limiting, caching, TLS.

### Phase 2 — round-robin (Aug 22)
**Built:** a `Balancer` interface with a `RoundRobin` implementation that cycles through a fixed backend list using an atomic counter. `-backend` became a repeatable flag.
**Concepts:** choosing a balancing algorithm (round-robin vs. random vs. weighted vs. least-connections, and why round-robin first); why the counter has to be safe under concurrent requests.
**Also:** `echobackend`, a small fake backend you can run several copies of, which made manual testing practical.

### Phase 3 — active health checks (Aug 23)
**Built:** a background checker that polls each backend's `/health` on its own timer. Unhealthy backends are skipped by the balancer. If every backend is down, the proxy returns a clean 502 instead of panicking or dialing nothing.
**Concepts:** active vs. passive health checking; one goroutine per backend; probe timeouts; why you never route to a known-dead backend.
**Known gaps carried forward:** no passive checks (marking a backend down from real request failures), no flap damping, no slow-start on recovery.

### Phase 4a — timeouts and backpressure (Aug 24)
**Built:** a time limit on the whole backend round trip (headers *and* body), and a `MaxConcurrent` middleware, a counting semaphore that rejects request N+1 with a 503. Handler order is `Logging → MaxConcurrent → proxy`.
**Concepts:** concurrency limits vs. rate limits (bounds *how many at once* vs. *how many per second*, different failure modes); what a timeout does at the TCP level; the `defer cancel()` trap that would silently truncate response bodies.

### Phase 4b — bounded FIFO queue (Aug 24)
**Built:** instead of instantly rejecting requests over the limit, a bounded waiting line with a per-request wait timeout. When a slot frees up, it is handed directly to the longest-waiting request.
**Concepts:** why queues must be bounded; fairness (FIFO hand-off); the "give-up race," where a request that times out at the same moment a slot is handed to it could leak that slot forever. PR review caught a real slot-leak race, which was fixed.

### Hotfixes (Sep 5)
- **PR #6:** moved the health-status update out of `main()` and into the `healthcheck` package, so the checker no longer depends on the balancer's algorithm.
- **PR #7:** extracted `internal/targetgroup`, a standalone object that owns "which backends are up right now?", written to by the health checker and read by the balancer. Also **repaired a real bug**: the checker was logging probe results but never reporting them, so unhealthy backends kept receiving traffic. Added a `Generation` counter so a future algorithm (consistent hashing) can cache derived state and rebuild only when membership changes.
**Concepts:** where shared state belongs; which direction dependencies point and who declares the interface in Go; shared state behind a mutex vs. message passing over channels; level-triggered vs. edge-triggered signals (a lost health update self-heals on the next probe).

## 7. What's next (plan as of Aug 24; confirm it still fits)

1. **Phase 5: global rate limiting.** Caps requests admitted *per unit time*, distinct from the concurrency limiter. Token bucket is the natural first algorithm.
2. **Phase 6: per-client rate and concurrency limiting.** Tested with several simulated clients, one deliberately exceeding its limit.
3. **Phase 7: consistent hashing.** A switch from admission control to routing, and the natural answer to the long-deferred "backends are fixed at startup" weakness. The `TargetGroup` generation counter was added to prepare for it.

Still-open weaknesses from earlier phases: no passive health checks or circuit breaking, no retries to a different backend, no flap damping or slow-start, no weights, static backend membership.
