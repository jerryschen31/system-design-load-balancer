# Phase 3: Active health checks

- **Branch:** `phase-3-active-health-checks`
- **PR:** opened from this branch into `build`
- **Status:** complete

## 1. What was built

The load balancer now proactively tracks whether each backend is actually able to serve traffic, instead of only discovering a dead backend when a real client request to it fails. A background checker polls each backend's `/health` endpoint on its own schedule; round-robin selection now skips any backend currently marked unhealthy.

Concretely:
- `internal/healthcheck` — new package. A `Checker` runs one independent polling goroutine per backend (a ticker per backend, not one shared loop), each doing `GET <backend>/health` with a per-probe timeout, and reporting the result through a caller-supplied callback.
- `internal/balancer` — `RoundRobin` now carries per-backend health state (`SetHealthy`) alongside the original fixed backend list, and `Next()` cycles only over the currently-healthy subset. If every backend is unhealthy, `Next()` returns `nil` rather than picking a known-dead backend.
- `internal/proxy` — handles `Next() == nil` by failing the request with a clean 502 ("no healthy backends available") instead of panicking or dialing an empty host.
- `cmd/echobackend` — gained `GET /health` (reports its current simulated health) and `POST /health/toggle` (flips it), so a single running process can be driven into "up but health-check-failing" state for manual testing, distinct from killing the process outright.
- `cmd/loadbalancer` — wires the checker's lifecycle into `main`: new `-health-check-interval`, `-health-check-timeout`, `-health-check-path` flags; the checker's context is cancelled on the same shutdown signal the HTTP server already listens for.

Deliberately out of scope for this phase: passive health checks (marking a backend down from real request failures), weighted/least-connections selection, gradual traffic ramp-up for a recovering backend ("slow start"), and the liveness/readiness split Kubernetes uses — all flagged below as follow-ups.

## 2. System Design concepts & considerations

- **Active vs. passive health checking.** Active: the load balancer generates its own out-of-band requests to a health endpoint, independent of real traffic, and can catch a silently hung backend even during an idle period. Passive: infer health from real proxied requests' outcomes, at zero extra traffic cost, but only after a real client has already eaten a failure, and blind during idle periods. Chose active first because it's the mechanism that actually prevents a client-visible failure, which is the sharper motivating problem from phase 2; passive is a natural, separable follow-up.
- **Multiple related fields needing one atomic update, and why that calls for a mutex instead of a lone `sync/atomic` value.** Phase 2 established that a single counter needing a single fetch-and-add is exactly what `atomic.Uint64` is for. This phase's health state is different in kind: `SetHealthy` has to update a per-backend status map *and* rebuild the derived "currently healthy" slice as one consistent step — there's no single CPU instruction that does both, so `RoundRobin` now holds a `sync.Mutex` guarding the map, while `Next()` still reads a separately-swapped `atomic.Pointer[[]*url.URL]` lock-free. This is the concrete case phase 2's notes predicted: "a mutex would be the right tool if the balancer later needs to update multiple related fields ... as one consistent unit."
- **Read-heavy/write-light state via copy-and-swap.** `Next()` is called on every request's own goroutine and must never block waiting on a health-check goroutine's mutex. `SetHealthy` builds an entirely new healthy slice and atomically swaps a pointer to it, rather than mutating a shared slice in place — so a `Next()` call that loaded the pointer a moment ago is still looking at something complete and internally consistent, never a half-rebuilt slice. This is the same "swap an immutable snapshot" shape phase 2's notes flagged as the likely answer to safely changing backend membership.
- **One polling goroutine per backend vs. one shared sequential loop.** A single loop that checks backends one after another has its total cycle time grow with backend count, and a hanging backend delays every other backend's check behind it. Per-backend goroutines, each on their own ticker, check in parallel and are independent of each other's latency — the standard shape for this in production systems. The cost: `SetHealthy` now has genuine concurrent, independent writers (multiple backends' goroutines can report at the same instant), which is what actually created the mutex-worthy state described above; with a single sequential checker loop there'd have been only one writer and the atomic-vs-mutex question wouldn't have come up yet.
- **Fail loud vs. fail silent when every backend is down.** Considered quietly falling back to routing to *some* backend even when all are marked unhealthy (better than nothing?) versus returning a clean 502. Chose 502: routing to a backend already known to be failing its health check just trades an honest, fast failure for a slower, still-guaranteed one, and masks the real problem (every backend is down) from whoever's watching error rates.
- **Optimistic vs. pessimistic cold start.** New backends start marked healthy immediately, rather than withheld from traffic until their first health check passes. Optimistic start is simpler and keeps this phase's scope to exactly "check and exclude," at the cost of a startup window where an actually-broken backend can receive traffic until its first failed check. This is the same distinction Kubernetes splits into separate liveness and readiness probes — noted explicitly as a real simplification to revisit in a later phase, not an oversight.

## 3. Design conversation summary

Phase 2's notes had already named the next problem precisely: round-robin has no notion of "down," so a dead backend keeps receiving every Nth request. The first real decision this phase was active vs. passive health checking — walked through the trade-off (extra background traffic and a new concurrency surface, vs. cheap but reactive and blind during idle periods) and chose active, since it's the version that actually stops a client from ever hitting a known-dead backend, which was the sharper motivation. Passive was set aside as a distinct, addable-later mechanism rather than a refinement of active checking.

Before writing any code, the file/function shape was laid out and reviewed: a new `internal/healthcheck` package owning the polling loop, `RoundRobin` gaining a `SetHealthy` method and health-aware `Next()`, `proxy.go` handling a `nil` target, and `echobackend` gaining a way to simulate "up but failing health checks" for manual testing distinct from killing the process. Two concrete calls were flagged for explicit sign-off rather than made silently: backends start healthy by default (optimistic), and an all-unhealthy balancer returns 502 rather than degrading to routing anywhere. Both were confirmed, with the explicit note that a future phase can build out separate liveness/readiness-style states closer to Kubernetes' model, rather than trying to fold that distinction in now.

Implementing the checker surfaced the concurrency design point flagged as a prediction back in phase 2: unlike the single counter, `SetHealthy` touches two related pieces of state (a status map entry and the derived healthy slice) that must change together, which is exactly the case where a mutex earns its place instead of a bare atomic. Choosing per-backend goroutines (rather than one sequential loop over all backends) for the checker was what actually made this concrete — it means `SetHealthy` has genuinely concurrent, independent writers, not just concurrent readers against one writer.

The manual walkthrough (three real `echobackend` processes plus a real `loadbalancer`, all on localhost) was where the design actually got proven, not just the automated suite: toggling one backend's `/health/toggle` to failing showed it fall out of the round-robin rotation within one health-check interval, purely from its own `/health` responses -- no request to it was ever allowed to fail first. Toggling it back showed it rejoin at its full 1/3 share immediately, with no ramp-up, which is precisely the thundering-herd-on-recovery weakness captured as a stress test below. Marking all three backends unhealthy in turn produced a clean, fast 502 from the load balancer itself, confirming the fail-loud design choice end to end.

## 4. Code changes

- `internal/healthcheck/healthcheck.go` — `Checker` type; `NewChecker` (panics on empty backend list or nil callback, same posture as `balancer.NewRoundRobin`); `Start` launches one goroutine per backend; each probe uses `context.WithTimeout` per request and treats connection errors, non-2xx status, and timeout identically as "unhealthy."
- `internal/healthcheck/healthcheck_test.go` — healthy/unhealthy-status/timeout detection, recovery detection over multiple checks on the same backend, and a context-cancellation test asserting polling stops (allowing at most one already-in-flight probe to complete).
- `internal/balancer/roundrobin.go` — `all []*url.URL` (immutable), `status map[string]bool` + `sync.Mutex`, `healthy atomic.Pointer[[]*url.URL]`; `SetHealthy` rebuild-and-swap; `Next()` reads the healthy pointer and returns `nil` when empty; `Balancer` interface gained `SetHealthy`.
- `internal/balancer/roundrobin_test.go` — optimistic-start, skip-unhealthy, all-unhealthy-returns-nil, unknown-backend-is-ignored, and a concurrent `SetHealthy`-vs-`Next()` flapping test meant to be run under `-race`.
- `internal/proxy/proxy.go` — `errNoHealthyBackends`; a `roundTripperFunc` adapter (the same "function implements an interface" idiom as `http.HandlerFunc`) used as a custom `Transport` that fails fast on an unset target instead of attempting to dial an empty host.
- `internal/proxy/proxy_test.go` — `TestNoHealthyBackendsReturns502`.
- `cmd/echobackend/main.go` — `atomic.Bool` health state; `newHealthHandler` (200/503 based on state); `newToggleHandler` (POST-only, flips state); routing moved from a single handler to an `http.ServeMux`.
- `cmd/echobackend/main_test.go` — health-reflects-state and toggle-flips-and-rejects-GET tests.
- `cmd/loadbalancer/main.go` — new health-check flags; `Checker` constructed and started against a cancellable context tied to the existing shutdown signal.
- `cmd/loadbalancer/integration_test.go` — new file; end-to-end tests wiring real `balancer` + `healthcheck` + `proxy` together (see Testing below).

## 5. Testing

### Functional tests
- `internal/healthcheck`: a checker correctly reports healthy (200), unhealthy (non-2xx), and unhealthy (timeout) from a single probe; detects a later recovery on the same backend; stops polling once its context is cancelled.
- `internal/balancer`: fresh backends start healthy; `SetHealthy(false)` removes a backend from the `Next()` cycle and `SetHealthy(true)` restores it; all-unhealthy yields `nil`; `SetHealthy` on an unrecognized URL is a no-op.
- `internal/proxy`: an all-unhealthy balancer produces a 502, not a panic or hang.
- `cmd/echobackend`: `/health` reflects current state; `/health/toggle` flips state on POST and rejects GET.
- `cmd/loadbalancer` (`TestIntegration_ChecksRouteAroundUnhealthyBackend`): a backend already failing its health check before the checker's first probe never receives a single real request once the checker has had time to run.

### Non-functional / stress tests
- **Concurrent `SetHealthy` vs. concurrent `Next()`** (`TestRoundRobinConcurrentSetHealthyAndNext`, `internal/balancer`) — one flapping goroutine per backend calling `SetHealthy` in a tight loop, concurrently with 20 goroutines hammering `Next()`, for 100ms, run under `-race`. No assertion on distribution (the state is intentionally always in flux); the test exists so the race detector can catch a genuine data race in the map/pointer-swap design.
- **Thundering herd on health-check recovery** (`TestStress_RecoveredBackendImmediatelyGetsFullShare`, `cmd/loadbalancer`) — confirmed and left as a documented weakness, not fixed this phase. A 3-backend setup: one backend starts unhealthy, confirmed to receive zero of a 30-request burst; then it's flipped healthy, and the moment the checker's callback confirms detection (no fixed sleep — the test waits on the actual detection event), a fresh 90-request concurrent burst is fired. The recovered backend received *exactly* an even 1/3 share (30 of 90) on the very first burst after detection — proof there's no gradual ramp-up. Documented explicitly as a real production risk: a backend recovering from something like a cold cache or a database reconnect can be slammed at full concurrency immediately and knocked back down before it's actually ready.
- **Continuous concurrent traffic through a rapidly flapping backend** (`TestStress_ConcurrentTrafficSurvivesHealthFlapping`, `cmd/loadbalancer`) — one backend's health flips every 10ms via a background goroutine while 200 concurrent requests run through the load balancer, with a real health checker concurrently mutating the balancer's routing state. Asserted every response is a clean 200 or 502 — never a hang, panic, or unexpected status — and that the stable backend absorbed traffic throughout.
- **Manual walkthrough** (outside the automated suite) — three real `echobackend` processes behind a real `loadbalancer` process on localhost. Verified round-robin across all three when healthy; verified a backend toggled to `/health/toggle`-failing was fully excluded from rotation within one health-check interval without ever failing a real client request; verified it rejoined at full share immediately on recovery; verified all three toggled unhealthy at once produced a clean, fast 502 from the load balancer.
- Phase 1 and phase 2's existing stress tests (slow backend outliving its own timeout, 50 concurrent requests handled in parallel, burst against an unreachable backend, exact-split concurrency test for the atomic counter) still pass unchanged.

## 6. Known weaknesses / open questions

- **No slow-start / gradual ramp-up for a recovering backend.** Directly demonstrated by `TestStress_RecoveredBackendImmediatelyGetsFullShare`: a backend goes from 0% to its full round-robin share the instant it's detected healthy. Production balancers (e.g. Envoy's slow-start mode) ramp a recovered backend's traffic share up gradually instead. Natural follow-up once weighted selection exists, since slow-start is essentially a time-varying weight.
- **No passive health checking.** A backend that's up but degraded in a way its `/health` endpoint doesn't reflect (e.g. a specific route is broken but `/health` is a trivial handler) will keep receiving traffic. Passive checks (tracking real request failure rates per backend) would catch this and complement active checks, as originally scoped out at the top of this phase.
- **No liveness/readiness split.** Every backend starts optimistically healthy at process start, so a backend that's actually broken from boot still receives traffic until its first failed check. Kubernetes' liveness (is it alive) vs. readiness (is it ready for traffic) distinction directly addresses this and is a reasonable model for a later phase, as discussed explicitly during design.
- **No weighting or load-aware selection** — carried over from phase 2, unchanged.
- **Still no timeout on backend responses, no backpressure/connection limits, no TLS** — carried over from phase 1, unchanged.
- **No live backend membership changes (add/remove backends without a restart)** — carried over from phase 2. Health checking doesn't fully solve this on its own: it changes which of a *fixed* set of backends is currently eligible, but the set itself (`RoundRobin.all`) is still fixed at construction. Genuinely adding or removing a backend at runtime is still a distinct, deferred feature.
