# Phase 4a: Backend timeouts and a concurrency limiter (no queue)

- **Branch:** `phase-4a-timeouts-backpressure`
- **PR:** opened from this branch into `build`
- **Status:** complete

## 1. What was built

Phase 3 gave the load balancer a way to *know* which backends are healthy. It still had no way to protect *itself* from a backend, or from too much traffic at once — a hung backend could hold a proxied request open indefinitely, and there was no ceiling on how many requests the load balancer would accept and try to serve concurrently. Phase 4a closes both gaps:

- `internal/proxy` — every backend request is now wrapped in `context.WithTimeout`, bounding the entire round trip (headers + full body) to a configurable `backendTimeout`. A backend that doesn't respond in time gets a clean 502 ("backend request timed out"), not an indefinite wait. `backendTimeout <= 0` is an explicit opt-out that restores the old wait-forever behavior.
- `internal/middleware` — a new `MaxConcurrent(n)` middleware caps how many requests the load balancer will process at once, using a buffered channel as a counting semaphore. The (n+1)th concurrent request is rejected immediately with 503 — **not queued**. A bounded wait queue is deliberately out of scope for this phase (see "4b" below) so the fail-fast mechanism could be built and proven correct on its own first.
- `cmd/echobackend` — gained `GET /sleep?seconds=N` (default 2s, capped at 30s), which blocks for the requested duration unless the request's context is cancelled first (racing `time.After` against `r.Context().Done()`, the same idiom `/hang` already used). It's the fixture that makes both new features demonstrable by hand: a controllable slow response for the timeout, and something that can be made to "pile up" concurrently for the limiter.
- `cmd/loadbalancer` — new `-backend-timeout` (default 10s) and `-max-concurrent` (default 100) flags; the composed handler chain is now `Logging → MaxConcurrent → proxy`, in that specific order (see below for why).

Deliberately out of scope: a bounded wait queue for requests over the concurrency limit (phase 4b, next), retries against a different backend on failure, rate limiting (distinct from concurrency limiting — see design discussion), and passive health checking / circuit breaking (still phase 3's known gap, now sharpened by this phase's discussion).

## 2. System Design concepts & considerations

- **Concurrency limit vs. rate limit — they bound different things.** A rate limit caps how many requests are *admitted* per unit of time, regardless of how long each takes. A concurrency limit caps how many are *open at once*, regardless of how fast they arrive. The failure mode this phase actually protects against — a hung or slow backend tying up load-balancer resources (goroutines, sockets) — is a concurrency problem, not a rate problem: one client sending one request per second, each taking ten seconds to finish, satisfies any reasonable rate limit while concurrency climbs toward ten in steady state. Rate limiting is a real, separate control (abuse prevention, per-client fairness) flagged as a distinct future feature, not folded into this phase.
- **Where to bound a "backend timeout": headers only, or headers + body?** Chose the whole round trip — from request sent to response body fully read — because that's what "the backend must finish responding within N seconds" should mean. The mechanism (`context.WithTimeout` layered onto the request's own context) enforces this by simply running for the full duration regardless of what phase of the response is in progress.
- **When to release a timeout's resources: right after `RoundTrip` returns, or after the body is consumed?** This turned out to be a genuine, non-obvious bug risk, not a stylistic choice. `RoundTrip` returning only means headers arrived — `httputil.ReverseProxy` still streams the body afterward by reading `resp.Body`. Calling the timeout's `cancel()` immediately (the naive placement, right next to `context.WithTimeout`) would invalidate the context before that streaming happened, silently truncating any response whose body didn't fully arrive in the very first read — which would pass every test with a small response body and only surface on real, larger payloads. The fix, `cancelOnCloseBody`, defers `cancel()` to `resp.Body.Close()`, which `ReverseProxy` already calls exactly once, at the true end of the body. `TestBackendTimeoutAllowsSlowStreamedBodyWithinBudget` is a regression test built specifically to catch a reintroduction of the naive version.
- **Fail-fast rejection vs. a bounded wait queue, for the concurrency limiter.** A queue smooths short bursts (a client arriving just before a slot frees up doesn't have to fail) but isn't free: it needs its own capacity limit *and* a max wait time (otherwise a queued request doesn't fail faster than an unbounded wait, it just fails invisibly later, after the client has already been kept waiting the whole time with no signal anything was wrong). Chose to ship the simpler fail-fast version first, prove it's correct in isolation, and add the queue as a deliberately separate phase (4b) with its own two knobs.
- **Middleware composition order is a real design decision, not incidental.** The handler chain is `Logging(MaxConcurrent(proxy))` — `Logging` has to be outermost so it observes and logs *every* request, including the ones `MaxConcurrent` rejects with a 503 before they ever reach the proxy. Reversing the order would make overload events invisible in the logs, which defeats the point of having them. This is the same category of "composition order changes what's actually true" point phase 3 raised about `SetHealthy`/`Next()` — passing every individual test doesn't guarantee the property you actually wanted.
- **Why the LB can't be the layer that permanently removes a broken backend.** Discussed while reasoning about how a circuit breaker (a phase 5 candidate for passive health checking) would ever mark a backend healthy again: the standard pattern is open → cool-down → half-open trial → closed, with the cool-down growing (capped) on repeated failure, cycling indefinitely rather than ever declaring the backend permanently gone. The load balancer's health signal genuinely can't distinguish "dead forever" from "mid-deploy" or "behind a healing network partition" — that decision belongs to a layer with more context (an orchestrator replacing a pod, an autoscaling group deregistering an instance, a human editing config), the same layered-responsibility split real infrastructure (Kubernetes readiness probes + Deployments, AWS Target Group health checks + ASG replacement) already makes.
- **Why "just retry on a different backend" isn't a free win for a timed-out request.** Two independent hazards, not one: retry storms (retrying against other backends the instant one is slow adds load to the fleet exactly when it's least able to absorb it) and idempotency (a request that already reached the backend and executed a non-idempotent side effect — like a `POST` — can't be safely retried without risking a duplicate effect, unless the backend supports an idempotency key). HTTP's own idempotent-method list (`GET`/`HEAD`/`OPTIONS`/`PUT`/`DELETE`) is necessary but not sufficient: a request can fail *after* being fully sent but before a response is known, which is genuinely ambiguous regardless of method. Flagged as a real, separate future phase rather than something to bolt on to this one.

## 3. Design conversation summary

The phase started from a review of phase 3's own "known weaknesses" list, which named three real candidates for what to build next: backend self-protection (timeouts/backpressure), smarter selection algorithms (weighted/least-connections), and passive health checking. Backpressure was chosen because it's a correctness/safety gap dating back to phase 1, not an optimization — "what happens when a backend hangs and everyone keeps sending it traffic" is also one of the most common System Design interview follow-ups for load balancers.

Before writing code, backpressure was scoped into "4a" (timeouts + a fail-fast concurrency limiter, no queue) and "4b" (a bounded queue with its own wait-timeout, layered on top of 4a) as two deliberately separate slices, rather than building the queue in from the start — a queue adds two more knobs (capacity, max wait) worth reasoning about on their own once the simpler mechanism is proven.

A significant side discussion clarified concurrency limits vs. rate limits from first principles before any code was written, since the two are easy to conflate but protect against different failure modes — this shaped the decision that a semaphore (bounding *how many*, not *how fast*) was the correct primitive, not a token-bucket rate limiter.

Testing methodology was deliberately carried over from phase 3's established practice: no fixed-sleep-based assertions for anything timing-sensitive. For the `/sleep` endpoint, the plan was refined mid-discussion — the user proposed a real `/sleep?seconds=N` backend endpoint for manual/`hey`-style load testing; the gap identified was that it can't, by itself, deterministically prove an *exact* concurrency boundary (an N-vs-N+1 admission test) without racing goroutine scheduling. Resolved by using both: `/sleep` on the real `echobackend` binary for the manual walkthrough and coarse stress tests, and an inline `arrived`/`release` channel-gate pattern (matching `toggleBackend` from phase 3's integration tests) for the precise automated boundary tests.

Implementing the backend timeout surfaced a real, non-obvious bug risk before it ever shipped: naively placing `defer cancel()` next to `context.WithTimeout` would cancel the round trip's context the instant `RoundTrip` returned — before `ReverseProxy` had streamed the response body — silently truncating any response whose body arrived in more than one read. This was caught during design (not discovered via a failing test after the fact) by walking through exactly what "`RoundTrip` returns" means at the mechanism level, and fixed with `cancelOnCloseBody`, with a dedicated regression test built to catch any future reintroduction of the naive version.

A separate thread worked through what actually happens, end to end, when a backend times out: the load balancer's `Transport` doesn't just stop waiting locally, it closes the underlying TCP connection to the backend; the backend's own `net/http` server detects that closed connection and cancels the in-flight handler's `r.Context()` — which is the exact signal `/sleep`'s `select` is built to catch. If a backend ignored that cancellation and finished anyway, its eventual write would fail against an already-closed socket (a "broken pipe"), not get silently forwarded or dropped by choice — the response simply never has anywhere left to go. This walkthrough directly motivated why `/sleep` honors `ctx.Done()` rather than always sleeping the full duration: a real backend that ignores cancellation isn't helping anyone by finishing, it's burning resources on a request that provably can't succeed anymore.

The manual walkthrough (two real processes: `echobackend` and `loadbalancer` on localhost, driven with real `curl`) proved the interaction between the two new features directly, including a happy accident: an early demo set `-backend-timeout 2s` with `/sleep?seconds=3`, which meant the "held" requests never actually completed — they were cut off by the backend timeout at 2.0s (502), exactly matching the scenario worked through earlier in discussion (a request arriving 1 second before a slot would have freed up gets treated identically to one arriving 9 seconds before, because `MaxConcurrent` has no notion of "how soon" — only "is there room right now"). A follow-up demo with `sleep=1s` against the same `backend-timeout=2s` showed the intended happy path: three requests held a slot for ~1s and completed with 200, two more arriving mid-flight were rejected with 503 in under a millisecond, and a fresh batch fired after the first completed proved the freed slots were genuinely reusable.

## 4. Code changes

- `internal/proxy/proxy.go` — `New` gains a `backendTimeout time.Duration` parameter; `roundTripperFunc`'s `Transport` wraps the outbound request in `context.WithTimeout(r.Context(), backendTimeout)` when `backendTimeout > 0`; new `cancelOnCloseBody` type defers the timeout's `cancel()` to `resp.Body.Close()` instead of immediately after `RoundTrip` returns; `ErrorHandler` gains an `errors.Is(err, context.DeadlineExceeded)` case producing a specific "backend request timed out" 502 body.
- `internal/middleware/concurrency.go` — new file. `MaxConcurrent(n int) func(http.Handler) http.Handler`; panics on `n <= 0` (same posture as `proxy.New`'s nil-balancer panic and `healthcheck.NewChecker`'s interval/timeout checks); a buffered `chan struct{}` of capacity `n` as a counting semaphore, acquired via non-blocking `select`/`default` (fail-fast, not queued) and released via a deferred receive once the wrapped handler returns.
- `internal/middleware/concurrency_test.go` — new file. Deterministic boundary test (`arrived`/`release` channel gate: exactly n admitted and held, further concurrent requests rejected immediately without ever blocking, slots reusable after release) and a panic-on-invalid-n test.
- `internal/middleware/logging.go` — package doc comment updated to reflect the concurrency limiter landing.
- `cmd/echobackend/main.go` — `parseSleepSeconds` (pure, testable parsing/capping logic) and `newSleepHandler` (races `time.After` against `r.Context().Done()`, same idiom as `newHangHandler`); registered at `/sleep`.
- `cmd/echobackend/main_test.go` — parsing/capping table test, fast-path response test, invalid-input test, and a cancellation test using an already-cancelled context (proves the handler returns promptly instead of sleeping the full duration).
- `cmd/loadbalancer/main.go` — new `-backend-timeout` (default 10s) and `-max-concurrent` (default 100) flags; handler composition changed to `middleware.Logging(logger)(middleware.MaxConcurrent(*maxConcurrent)(proxy.New(rr, *backendTimeout, logger)))`.
- `internal/proxy/proxy_test.go` / `stress_test.go` — all existing `New(...)` call sites updated to pass `0` (opt-out, preserving prior behavior exactly) except where a test is specifically about timeouts; `TestStress_SlowBackendHasNoTimeout` renamed to `TestStress_DisabledTimeoutWaitsIndefinitely` (proves the opt-out still works, since it's no longer the default weakness it used to document); two new tests added: `TestBackendTimeoutReturns502` (proxy's own timeout cuts a slow backend off without relying on the client's timeout) and `TestBackendTimeoutAllowsSlowStreamedBodyWithinBudget` (the `cancelOnCloseBody` regression test).
- `cmd/loadbalancer/integration_test.go` — existing `proxy.New(...)` call sites updated to pass `0`; new `TestIntegration_MaxConcurrentProtectsFullStack` proves the limiter works correctly composed with the real handler chain (not just in isolation), including that rejections happen before the proxy ever picks or dials a backend.

## 5. Testing

### Functional tests
- `internal/proxy`: backend timeout produces a 502 with a specific "backend request timed out" body, well before the backend's own (much longer) delay, with no timeout set on the client; a streamed multi-chunk response completes intact when total transfer time is within budget (the `cancelOnCloseBody` correctness proof); the `backendTimeout <= 0` opt-out still waits indefinitely, relying only on the client's own timeout.
- `internal/middleware`: `MaxConcurrent` admits exactly `n` concurrent requests and rejects further concurrent requests immediately (not queued, proven by the test deadlocking if it were queuing instead — see below); slots are reusable after release; construction panics on `n <= 0`.
- `cmd/echobackend`: `/sleep` parsing/capping logic tested directly (pure function, no actual sleeping in the test); fast-path (`seconds=0`) responds near-instantly; invalid input is a 400; an already-cancelled request context causes the handler to return promptly rather than sleeping the full requested duration.
- `cmd/loadbalancer`: `TestIntegration_MaxConcurrentProtectsFullStack` proves the limiter, composed in the real order with `Logging` and `proxy` against a real backend, admits exactly `n` and rejects a full burst of extras immediately.

### Non-functional / stress tests
- **Immediate rejection, not queueing** (`TestMaxConcurrentAllowsExactlyNInFlight`, `internal/middleware`, and the integration equivalent) — the "extra" requests are fired while the held requests' release channel is still open; if `MaxConcurrent` were queuing rather than rejecting, waiting for those extra requests to complete would hang until the test's own timeout. That hang is the actual proof of fail-fast behavior, not a separate assertion layered on top.
- **Streamed body under a real timeout budget** (`TestBackendTimeoutAllowsSlowStreamedBodyWithinBudget`, `internal/proxy`) — guards specifically against the `cancelOnCloseBody` timing bug described above; a response that takes real, non-trivial time to fully arrive (multiple flushed chunks) but stays within `backendTimeout` must not be truncated.
- **Manual walkthrough** (outside the automated suite; real `echobackend` + `loadbalancer` processes on localhost, driven by `curl`) — confirmed: (1) `-backend-timeout 2s` cuts off a `/sleep?seconds=5` request at ~2.0s with a 502, and the backend's own log independently confirms it observed the cancellation at the same instant, not just that the client saw a timeout; (2) with `-max-concurrent 3`, 3 requests holding all slots plus 2 more fired mid-flight produced exactly 3 timeouts/completions and 2 immediate 503s, in every combination tried (including one where the held requests themselves got timed out rather than completing, since `-backend-timeout` was shorter than the sleep duration used — an unplanned but exact real-world confirmation of the "MaxConcurrent doesn't know how close a slot is to freeing up" discussion); (3) after slots freed, a fresh batch of requests reused them successfully with sub-millisecond responses.
- Phase 1-3's existing functional and stress tests (slow backend, concurrent request handling, unreachable backend bursts, health-check skip/recovery/flapping) still pass unchanged.

## 6. Known weaknesses / open questions

- **No bounded wait queue** — the whole motivation for phase 4b, next. Today, a client arriving one second before a slot would free up is rejected exactly as hard as one arriving nine seconds before (demonstrated directly in the manual walkthrough and in prior design discussion) — a queue with a short max-wait would let the near-miss case succeed while the client is at least aware it's waiting, rather than an unbounded wait that just delays an eventual failure invisibly.
- **No automatic retry against a different backend on timeout or failure** — deliberately deferred; requires deciding retry limits, which methods are safe to retry, and how to handle the ambiguous "request was sent, outcome unknown" case, none of which is free (see design discussion above on retry storms and idempotency).
- **No rate limiting** — concurrency limiting and rate limiting protect against different things (see design discussion); rate limiting (per-client fairness, abuse prevention) is unaddressed and would be a distinct feature, not a refinement of `MaxConcurrent`.
- **No passive health checking / circuit breaker** — carried over from phase 3, now sharpened: a backend that's healthy by `/health` but consistently timing out on real traffic (e.g. one broken route) will keep receiving its full traffic share indefinitely under today's design, since `backendTimeout` produces a clean 502 per request but never feeds that signal back into the balancer's health state.
- **`MaxConcurrent` is a single global limit, not per-backend** — one slow backend combined with the global concurrency cap being saturated can crowd out capacity that would otherwise be available for requests destined to healthy, fast backends. A per-backend limit (or a limit that accounts for which backend a request will be routed to) is a plausible future refinement, not addressed here.
- **Still no live backend membership changes, no TLS** — carried over from phases 1-3, unchanged.
