⏺ Step 2: Logging middleware wraps the request

  Plain-language shape first: every request needs to be timed and its outcome
  recorded, but the code that actually handles the request (further down the
  chain) shouldn't have to know anything about logging — it just does its job,
  and something wrapping it watches from the outside and reports what happened.
  That "watch from outside" pattern is what all three layers here use.

        ┌─────────────────────────────────────────────┐
        │ Logging wrapper                              │
        │   record start time                          │
        │   call inner handler ──────────────► (rest of chain)
        │   ◄────────────────── inner handler returns  │
        │   log: method, path, status, elapsed time     │
        └─────────────────────────────────────────────┘

  Now the code, internal/middleware/logging.go:32-40:

  return func(next http.Handler) http.Handler {
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
          start := time.Now()
          next.ServeHTTP(rec, r)
          logger.Printf("%s %s %d %s", r.Method, r.URL.Path, rec.status,
  time.Since(start))
      })
  })

  - Logging(logger) returns a function, not a handler directly — a function that
    takes a handler (next) and returns a new handler. This is the standard Go
    "middleware" shape: func(http.Handler) http.Handler. It's why main.go:107
    reads as middleware.Logging(logger)(...) — two chained calls, first to
    configure it with the logger, second to wrap the next layer.
  - http.Handler is an interface: anything with a ServeHTTP(ResponseWriter, 
    *Request) method satisfies it. http.HandlerFunc is a small adapter type —
    it's a plain function value that gets a ServeHTTP method attached to it, so
    an ordinary func(w, r) closure can be handed anywhere an http.Handler is
    expected.
  - The problem this middleware solves: the standard http.ResponseWriter
    interface only lets you write a status code, never read back what was
    written — so after next.ServeHTTP returns, there'd be no way to know if the
    inner handler responded 200, 502, or something else. statusRecorder (lines
    15-23) solves this by wrapping the real ResponseWriter and intercepting the
    WriteHeader call to stash the status in a field before passing it through —
    that's why rec, not the original w, gets passed to next.ServeHTTP.
  - start := time.Now() / time.Since(start) brackets the entire rest of the
    chain — MaxConcurrent, backend selection, and the actual backend round trip
    are all included in this timing. So the logged latency is "total time this
    request spent in the load balancer," not just proxy time.
  - The log line only fires after next.ServeHTTP(rec, r) returns — meaning after
    every layer below has finished. So this is the outermost wrapper: first to
    see the request coming in, last to do anything on the way out.

  What it does NOT do: it doesn't decide whether the request succeeds or fails,
  and it doesn't touch the request body or headers. It's purely an observer
  sitting around the outside of everything else.

⏺ Good catch — that name is genuinely confusing the first time. Let me untangle
  it.

  Plain-language model first: "serve" here doesn't mean "send a request out." It
  means the same thing as in "the restaurant serves customers" — you already
  have a customer (the incoming request) in front of you, and "serving" them
  means producing the meal (the outgoing response) for them. ServeHTTP is Go's
  name for "handle this incoming HTTP request and produce a response for it."
  It's a verb aimed at the request that already arrived, not an instruction to
  go make a new one.

  So by the time ServeHTTP is called, the parsing of what the client sent is
  already done — net/http's internals (the part I described in Step 1) already
  read the raw bytes off the TCP connection and built the *http.Request struct
  for you. ServeHTTP is just "now do something with it."

  What each parameter actually is, concretely:

  ServeHTTP(w http.ResponseWriter, r *http.Request)
                │                        │
                │                        └─ the INCOMING request, already
  parsed:
                │                           method, path, headers, body — all
                │                           read-only data describing what the
                │                           client sent you
                │
                └─ a WRITE-ONLY handle for the OUTGOING response.
                   Calling w.WriteHeader(200) or w.Write([]byte(...))
                   streams bytes back down the same TCP connection to
                   that same client, right now.

  - r (*http.Request) = what came in. You read from it (r.Method, r.URL.Path).
  - w (http.ResponseWriter) = what goes out. You write to it. There is no
    .Read() on it — it's not a request, it's the channel back to the client.

  So the confusing part is just: "ServeHTTP" sounds like it's about producing an
  HTTP request, but it's actually the standard name for "handle one
  request/response cycle." Every single handler in this codebase — the logger,
  the concurrency limiter, and eventually the reverse proxy itself — has this
  exact same method signature, because net/http only knows how to call one
  thing: something with a ServeHTTP(w, r) method. That's the whole http.Handler
  interface (one method, this one).

  Concretely in the logging middleware:
  - r arrives already containing the client's actual request.
  - rec (wrapping w) is handed to next.ServeHTTP(rec, r) — the next layer down
    writes the eventual response through rec, and because rec intercepts
    WriteHeader, the logger can see the status code that got written, after the
    fact.

  │  └────────────────┬──────────────────────────┘│

  └────────────────┬────────────────────────────────┘
                    ▼
          response sent to client

  So yes:
  1. Logging sees the request first (records start time), then hands off.
  2. MaxConcurrent decides: is there a free slot right now? If yes, take it and
     pass the request further in. If not, either queue (up to queueCapacity) and
     wait, or reject immediately with a 503 — in the reject/timeout case, the
     request never reaches the proxy at all.
  3. ReverseProxy (only reached if MaxConcurrent let it through) picks a backend
     via round-robin and forwards the request there.
  4. The response flows back the other way: ReverseProxy returns → MaxConcurrent
     releases its slot → Logging records the final status and total elapsed
     time, then that's what actually gets written back to the client.

❯ so next.ServerHTTP doesn't actually return with the response until the actual 
  response comes all the way back from the backend and from the inner

⏺ Exactly right — and it's worth being precise about how that's true, because
  ServeHTTP doesn't return a value at all (no return type), so "the response
  comes back" doesn't mean what it would in a normal function call.

  Plain-language model

  Calling next.ServeHTTP(w, r) is a blocking call — the calling goroutine sits
  parked at that line, doing nothing else, until the entire chain underneath it
  is completely done handling the request. There's no separate "get the response
  back" step — the response isn't a return value, it's bytes written directly
  onto the TCP connection while everything is still running, through w.

  Logging's goroutine, stack of blocked calls (top = currently doing work):

     ReverseProxy is copying backend's response body → w    ← actively running
     MaxConcurrent is blocked at next.ServeHTTP(...)         ← waiting
     Logging is blocked at next.ServeHTTP(...)               ← waiting

  All three of these are literally the same goroutine, just at different points
  in a call stack — like nested function calls in any language. Logging's call
  to next.ServeHTTP doesn't return until MaxConcurrent's call to its
  next.ServeHTTP doesn't return, which doesn't return until ReverseProxy has
  finished writing the full response (headers + entire body) to w, or given up
  with an error.

  Concretely, tracing it through this codebase

  - ReverseProxy.ServeHTTP (inside httputil.ReverseProxy, not code you wrote)
    does the real work last: send request to backend, read response headers,
    then copy the response body byte-by-byte from the backend connection to w —
    this copying is what actually sends bytes to the client. It only returns
    once that copy is finished (body fully streamed) or fails.
  - Only after that returns does middleware.MaxConcurrent's next.ServeHTTP(w, r)
    call (concurrency.go:189) unblock, letting defer l.release() run and free
    the slot.
  - Only after that does middleware.Logging's next.ServeHTTP(rec, r) call
    (logging.go:36) unblock, letting the log line on line 37 execute with the
    now-final rec.status and elapsed time.

  What this does NOT mean: it's not that a response object gets handed back up
  through the layers like a return value being passed up a call stack. The bytes
  go straight from ReverseProxy's copy loop, through w, out the socket, to the
  client — bypassing MaxConcurrent and Logging entirely in terms of data flow.
  What does flow back up is just control — "I'm done, you may proceed" — which
  is exactly why defer on release and the log line are able to run only after
  everything downstream is truly finished, not a moment sooner.

  That's also why the proxy's own cancelOnCloseBody trick (proxy.go:33-56, which
  you'll see in the last step) exists: ReverseProxy streams the body as part of
  this same blocking call, so a slow backend keeps everything above it blocked
  for the whole duration, not just until headers arrive.

❯ So why again do we need this statusRecorder struct ? Doesn't the              
  ResponseWriter have the response's status code ?                              

⏺ Good question — the short answer: http.ResponseWriter is an interface, and
  interfaces only expose the methods they declare. It doesn't matter what the
  concrete object behind it actually stores internally — if the interface's
  method set doesn't include a getter, you cannot call one.

  What the interface actually looks like

  type ResponseWriter interface {
      Header() http.Header
      Write([]byte) (int, error)
      WriteHeader(statusCode int)
  }

  That's it — three methods, all of them about writing. There is no StatusCode()
  int or anything similar. Logging's handler only ever receives a value of this
  interface type — that's literally what its parameter type is (func(w 
  http.ResponseWriter, r *http.Request)). So no matter what's going on
  underneath, all Logging can legally do with w is call Header(), Write(), or
  WriteHeader().

  Why there's no getter, concretely

  - The concrete type net/http actually gives you behind that interface does
    internally know its status once written — but that's a private
    implementation detail of net/http's internal type, not something the
    ResponseWriter interface contract promises you access to.
  - Interfaces in Go are a deliberate narrowing: whoever calls next.ServeHTTP(w,
    r) and passes w in has decided the callee gets exactly this interface's
    capabilities and nothing more — write access, not read access. That's an
    intentional design choice by the standard library, not an oversight: a
    response is something you produce, not something you inspect after the fact
    through the same handle.

  So what does statusRecorder actually do

  It doesn't extract a hidden status from the real w — it intercepts the write
  before it happens and remembers what was written, using Go's embedding:

  type statusRecorder struct {
      http.ResponseWriter   // embedded: statusRecorder automatically "inherits"
                             // Header(), Write(), WriteHeader() from whatever
                             // concrete ResponseWriter is stored here
      status int
  }

  func (r *statusRecorder) WriteHeader(status int) {
      r.status = status                    // 1. stash it in our own field
      r.ResponseWriter.WriteHeader(status) // 2. then actually forward the call
  }

   next.ServeHTTP(rec, r)
          │
          ▼
   inner handler calls rec.WriteHeader(502)
          │
          ▼
   statusRecorder.WriteHeader runs (our override, not the real one)
     ├─ rec.status = 502          ← now WE know it
     └─ forwards to the real ResponseWriter.WriteHeader(502)  ← client still
  gets it

  rec gets passed down instead of the original w (logging.go:36:
  next.ServeHTTP(rec, r)), so every layer below writes through rec, and every
  WriteHeader call anywhere downstream — proxy's ErrorHandler, or a successful
  response — necessarily passes through this override first, no matter how deep
  in the chain it happens. That's the trick: you can't add a method to an
  interface, but you can wrap it in a struct that intercepts the one call you
  care about and delegates the rest unchanged.

  One subtlety: if a handler calls w.Write(...) directly without ever calling
  WriteHeader explicitly (common for a plain 200 response), net/http implicitly
  calls WriteHeader(200) for you on the first Write. That still goes through
  statusRecorder's override since Write isn't overridden and falls through to
  the embedded field's Write, which is the real writer's Write — but that real
  writer's own internal WriteHeader(200) firing doesn't touch rec.status. Let me
  check that's not actually a bug here.
