  Q1: You are not passing "the entire roundrobin"

  Here's what actually happens at line 125, mechanically.

  healthcheck.NewChecker's parameter is declared as reporter HealthReporter — an
  interface with exactly one method. In Go, an interface value at runtime is
  two machine words:

    reporter (interface value, 2 words in memory)
    ┌─────────────────┬──────────────────────────────┐
    │ data pointer    │ itab pointer                 │
    │  → the *RoundRobin │  → method table for        │
    │    struct in heap  │    (*RoundRobin, HealthReporter)│
    └─────────────────┴──────────────┬───────────────┘
                                     │
                                     ▼
                          ┌──────────────────────┐
                          │ [0] SetHealthy       │   ← one entry. That's it.
                          └──────────────────────┘

  The itab (interface table) is built by the compiler and contains only the 
  methods the interface declares. Next is not in it. healthcheck cannot call
  rr.Next() — not "shouldn't", cannot; the code won't compile, because inside
  the package the only thing it has is a HealthReporter, and HealthReporter has
  one method.

  So the visibility you're worried about isn't there. What you're passing is
  closer to "a pointer plus permission to call one method" than "the whole
  object."

  Two more things that confirm the coupling is already thin:

  - healthcheck does not import balancer. balancer does not import healthcheck.
    Check the import blocks — they're genuinely independent packages. They only
    agree on *url.URL and bool.
  - HealthReporter is declared in healthcheck (the consumer), not in balancer
    (the producer). That is the Go convention, and it's the one that matters:
    the consumer states the narrowest thing it needs, and any producer that
    happens to have a matching method satisfies it without knowing the interface
    exists. Compare with Java/C#, where RoundRobin would have to write
    implements HealthReporter and thereby take a compile-time dependency on the
    healthcheck package. Go's structural satisfaction is what buys you the
    decoupling here.

  If you want the syntactically minimal version of what you described — "all it
  needs is the function" — that already works today, because HealthReporterFunc
  exists:

  healthcheck.NewChecker(..., healthcheck.HealthReporterFunc(rr.SetHealthy),
  ...)

  rr.SetHealthy on its own is a method value: Go creates a closure that captures
  rr as the receiver. So this is not less coupled than passing rr — it's the
  same pointer, wrapped in a func instead of an itab. It's a style preference,
  not a decoupling win. (The interface version is generally preferred once you
  might want a second method, and it gives the parameter a name in godoc.)

  Q2: What a channel would and wouldn't buy you

  Plain-language version first. Right now, when a probe finishes, the probing
  goroutine itself walks into the balancer's data structure and updates it — one
  continuous chain of calls, and the probe goroutine is blocked (briefly) while
  that happens. A channel would instead have the probe drop a note into a queue
  and immediately go back to probing; some other goroutine picks the note up
  later and does the update.

  The critical thing to see: the update still has to happen, and something still
  has to do it. A channel doesn't remove that work — it inserts a queue and a
  second goroutine in front of it, and now you own both.

  Shape A — today

    probe goroutine (backend A)
          │  synchronous call
          ▼
    SetHealthy(A,false) ──► lock mu, rebuild slice, swap atomic pointer
          │                                        │
          ▼                                        ▼
     back to ticker                    request goroutines read new slice

  One hop. No new lifecycle. Latency from "probe fails" to "routing changed" is
  microseconds.

  Shape B — channel consumed at the composition root (main)

    probe A ──┐
    probe B ──┼──► chan HealthEvent ──► fan-in goroutine (in main)
    probe C ──┘                              │
                                             ▼
                                       rr.SetHealthy(...)
                                             │
                                             ▼
                                lock mu, rebuild, swap pointer

  Notice where SetHealthy ended up: still on RoundRobin, still called with a 
  *RoundRobin. All you did was move the call site from healthcheck into main,
  and add a goroutine you now have to shut down. Your composition root gets more
  wiring, not less — which is the opposite of what commit b3f8c11 was trying to
  achieve.

  Shape C — channel consumed inside the balancer (actor model)

    probe A ──┐
    probe B ──┼──► rr.updates (chan) ──► rr's own goroutine ──► rebuild, swap
  pointer
    probe C ──┘                                                        │
                                                                       ▼
                                                request goroutines read via
  atomic load

  This is the real "share memory by communicating" version: one goroutine
  exclusively owns status, so mu disappears. But:

  - RoundRobin now needs a Start(ctx) and a shutdown path. It stops being a
    plain value you can construct and use.
  - Reads still need the atomic.Pointer, because 3000 concurrent request
    goroutines can't each do a channel round-trip to ask "who's next" — that
    would serialize your entire request path through one goroutine. So you keep
    the atomic and add a goroutine.
  - The Go team's own guidance (and Rob Pike's, despite the proverb): channels 
    are for transferring ownership and orchestrating; mutexes are for protecting
    shared state. Your healthy-set is shared state read by every request.
    That's the mutex/atomic case.

  The four questions any channel design forces you to answer

  These are the real System Design content here, and they generalize far past
  this repo:

  1. Buffering / backpressure. Unbuffered channel = the probe goroutine blocks
     until a consumer receives. If the consumer stalls, your health checks stall
     — a slow consumer silently degrades your failure detection. Buffered =
     events queue up, and routing lags reality by however deep the queue is.
  2. Drop policy. With a buffer, what happens when it's full? select { case ch 
     <- ev: default: /* drop */ } keeps probing at full speed but loses events.
     Whether dropping is safe depends on whether the channel carries state or 
     edges — see below.
  3. Ordering. You have one goroutine per backend, so events for a given backend
     are already totally ordered by that goroutine. A single shared channel
     preserves that. If you ever moved to a worker pool consuming the channel,
     you could apply A=false after A=true out of order and pin a live backend
     down permanently. That hazard doesn't exist in Shape A at all.
  4. Lifecycle. Who closes the channel? Closing from N producers is a panic risk
     (close on an already-closed channel panics; sending on a closed channel
     panics). The usual answer is a sync.WaitGroup over the producers plus a
     closer goroutine — more machinery.

  The insight that makes drop policy tractable

  Your health signal is level-triggered, not edge-triggered. Every probe
  re-reports the backend's current state, every interval — not "it changed." So
  a dropped or stale event self-heals within one -health-check-interval. Worst
  case is 5 seconds of stale routing, not permanent divergence.

  That's genuinely worth internalizing for interviews: the same distinction is
  why Kubernetes controllers re-list-and-reconcile rather than trusting a watch
  stream, and why BGP keepalives resend full state. Systems that resend state 
  tolerate lossy transport; systems that send deltas do not. Your changed bool
  is the one edge-triggered thing in the design — and it's derived at the
  consumer, which is the right place for it.

  What I'd actually propose: extract a health registry

  This addresses the real complaint (duplication + "why does the algorithm own
  this?") without adding a goroutine.

  Plain language: instead of the health checker talking to the balancer, both of
  them talk to a small shared object whose only job is to remember which
  backends are up. The checker writes to it. The balancer reads from it. Neither
  one knows the other exists.

                   ┌──────────────────────┐
     healthcheck ──┤  health.Registry     ├── balancer.RoundRobin
       (writer)    │  status map + mu     │      (reader)
                   │  healthy []*url.URL  │
                   │  behind atomic.Ptr   │
                   └──────────────────────┘
       writes: Set(backend, healthy) bool     reads: Healthy() []*url.URL

  Dependency arrows both point inward at a tiny type that depends on nothing.
  Compare to today, where the arrow points from healthcheck → balancer.

  Mapping that onto your existing code, one piece at a time:

  - The box's stored state is exactly today's RoundRobin.status, RoundRobin.mu,
    and RoundRobin.healthy fields — lifted out of roundrobin.go verbatim.
  - The write arrow is today's SetHealthy body, moved to the new type.
  - The read arrow is the single line healthy := *r.healthy.Load() at the top of
    Next() — it becomes healthy := reg.Healthy(), still a lock-free atomic
    load, so the hot request path doesn't change at all.
  - main constructs the registry once and hands the same pointer to
    balancer.NewRoundRobin(targets, reg) and healthcheck.NewChecker(..., reg, 
    ...).
  - healthcheck.HealthReporter stays exactly as it is. The registry satisfies it
    structurally.

  What this buys: least-connections, weighted RR, and consistent hashing all get
  health handling for free. roundrobin.go shrinks to counter arithmetic — which
  is the actual algorithm, and makes it much clearer in an interview writeup
  what round-robin is.

  There's a cheaper variant (embed the registry in RoundRobin so SetHealthy is
  promoted and main doesn't change at all) if you'd rather not touch the
  composition root — but the two-consumer version above is the one that
  genuinely inverts the dependency.

  The wrinkle worth knowing before phase 7

  Consistent hashing breaks the "just filter a list" model. When a node goes
  down, you can't filter it out per-request — the whole point of the ring is
  that a key maps to a position, and you'd have to walk the ring. You want the
  ring rebuilt when membership changes, not consulted-then-filtered on every
  request.

  So consistent hashing needs a change notification, not just a queryable
  registry. Which is where the callback shape comes back:

    Registry.Set(...) ──► did state change?
                              │ yes
                              ▼
                        notify subscribers ──► ring.rebuild()
                                          └──► metrics exporter
                                          └──► admin dashboard / status endpoint

  And that's where a channel or subscription list genuinely earns its 
  complexity: when there is more than one interested party. That's the decision
  rule I'd hold onto:

  ┌──────────────────────────┬──────────────────────────────────────────────┐
  │        Consumers         │                 Right shape                  │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Exactly one, known at    │ Direct call through a narrow interface       │
  │ compile time             │ (today)                                      │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ One, but the write path  │ Buffered channel + one consumer goroutine    │
  │ must not block           │                                              │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ Several, or they come    │ Registry + subscription (Subscribe() <-chan  │
  │ and go at runtime        │ Event or a slice of callbacks)               │
  └──────────────────────────┴──────────────────────────────────────────────┘

  You have exactly one consumer today. That's why the direct call is correct
  right now, and why adding a channel would be complexity you're paying for
  without a buyer.

  Q3: Consistent hashing — and why it changes the API now, not later

  This is the important one, so plain language first.

  Round-robin can look at the list of healthy backends fresh on every single
  request — it's just an array index, essentially free. Consistent hashing
  can't. Its routing structure is a sorted ring of hash positions (each backend
  placed at ~100–200 spots around a circle so removals only disturb a small
  arc). Building that ring means hashing hundreds or thousands of values and
  sorting them. You do that once when membership changes, not once per request.

  So consistent hashing needs to answer a question round-robin never asks: "has 
  the membership changed since the last time I built my ring?"

  There are two ways to answer that:

    PUSH                                    PULL (version stamp)

    pool.SetHealthy()                       pool.SetHealthy()
       │ detects change                        │ detects change
       ▼                                       ▼
    calls registered callbacks              bumps a generation number
       │                                       │
       ▼                                       ▼
    ring.rebuild() runs on the              ring notices gen changed on the
    health-check goroutine,                 next request, rebuilds then
    possibly under pool's lock

  Push means the pool holds a list of subscribers and calls into them. That's
  the callback-under-a-lock hazard again, it runs the rebuild on a health-check
  goroutine (so a slow rebuild stalls health checking), and it means the pool
  has to know about registration, ordering, and unregistration.

  Pull with a version stamp means the pool just increments a counter when
  something changes, and each consumer compares it against what it last saw. No
  callbacks, no goroutines, no lock inversion. The consumer that cares does the
  work, on a goroutine that actually needs the answer.

  This is a broadly reusable pattern, worth naming for interviews: it's the same
  mechanism as Kubernetes resourceVersion, etcd revisions, and HTTP ETag /
  If-None-Match. Publish a cheap version stamp alongside expensive derived data,
  and let consumers decide when to recompute.

  The one thing you must get right: the version and the data have to be
  published together, atomically. If a consumer could read generation 7
  alongside generation 6's backend list, it would cache a stale ring and never
  fix it. The fix is to put both in one immutable struct behind a single
  atomic.Pointer, so one pointer swap publishes both at once:

  // pool.Snapshot is immutable once published.
  type Snapshot struct {
      Healthy    []*url.URL // never mutated after publish — read only
      Generation uint64     // bumped on every actual membership change
  }

  So the answer to your question is: no refactor in phase 7, provided we add 
  Generation now. It's one field and one p.generation++ line. That's cheap
  insurance, and it's the difference between phase 7 touching pool and phase 7
  being purely additive.

  type Snapshot struct {

  Both get published by a single g.current.Store(&Snapshot{...}). If they were
